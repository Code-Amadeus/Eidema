# Eidema v1：记忆模块的职责与边界

日期：2026-10-23（Pacific/Auckland）。

状态：已确认的产品方向与职责边界；尚无运行时实现。初版已选择 Python + SQLite 的技术方向；本文不冻结数据表、公开 API 或具体性能参数，字段与关系见[初版数据模型](v1-data-model.md)。

## 1. 第一版目标

Eidema 是一个可供不同宿主应用使用的记忆与人格项目，Amadeus 是首个集成对象。**第一版聚焦记忆，继续使用宿主已有的人格配置与回复模型。**

初版部署目标是本地 Amadeus，同时保留其他宿主接入能力。多用户服务器与独立常驻服务不是本版的默认前提。

第一版要建立一条完整、可验证的路径：

> 用户明确记住 → 持久化 → 新会话召回 → 纠正或遗忘 → 重启后保持效果。

在这条路径可靠之后，加入可选的后台自动形成与整理。后台处理应改善跨会话连续性，并具有可观察、可限制的运行成本。

## 2. 范围

### 本版包含

- 有来源、受范围约束的跨会话召回。
- 用户明确保存的事实、偏好、要求和事件概述。
- 查看、纠正、遗忘及相应的派生数据失效。
- 允许来源的增量接收和可选的后台记忆形成。
- 有预算的去重、更新、合并与摘要整理。
- 为不同角色、用户和项目保持清楚的数据归属。
- 以内容和来源提供记忆，让宿主与现有人格配置决定如何表达。

### 后续方向

- 关系状态及关系摘要的自动推导。
- 互动习惯的自动成长。
- 自动人格演化、好感度、情绪或其他人格成长指标。
- 持久 agent 的定时工作与主动交互，交由宿主的独立调度组件。

共同发生的事件可以被记住，但本版不会据此计算“更信任用户”“关系更亲密”等状态。用户明确提出的互动要求仍属于可保存的记忆；这不等于系统自行推断互动习惯。

后续人格能力可以建立在本版的数据基础上，本版不预置没有实际消费者的关系字段或人格状态机。

## 3. 责任与数据归属

| 责任方 | 负责的内容 | 权威边界 |
| --- | --- | --- |
| 宿主应用 | 用户和角色身份、当前会话与项目、来源授权、原始对话、业务状态、执行回执 | 决定谁可以读写哪些内容，以及什么行动真正发生、获得了什么权限 |
| Eidema 记忆模块 | 记忆持久化、来源关联、有效性、检索、纠正、遗忘和后台整理 | 管理记忆及派生结果的生命周期；模型解释不会成为新的执行授权 |
| 宿主现有的人格配置与回复模型 | 用户定义的角色设定、当前请求、口吻和表达 | 使用有效记忆回答；核心人设不会被后台记忆整理悄悄改写 |

逻辑责任不要求独立数据库或服务。每类数据应有一个清楚的权威写入入口。

接入 Amadeus 时，复用其现有 Session、角色配置和 Work Ledger。Eidema 可以保存记忆所需的证据片段与引用，但不再建立一套权威聊天档案、人设副本或 Work 状态账本。

宿主负责提供稳定、不歧义的来源和身份引用。记忆的访问范围由宿主授予，并由记忆读写边界落实，不能由模型生成的名称、角色台词或记忆文本扩大。

**Amadeus 是持久 agent，后续需要独立的 Schedule / Persistent Runtime 组件。** 它拥有定时任务定义、触发、恢复、取消和派发状态；宿主执行系统拥有真实执行结果。Eidema 提供允许范围内的记忆并接收有来源的结果，记忆整理不会自行创建或修改 schedule。具体边界见[持久 agent 与调度组件](persistent-agent-scheduling.md)。

## 4. 记忆需要回答的四个问题

每条记忆至少应能解释：

1. **属于谁**：相关的用户、角色或项目身份。
2. **谁可以读取**：宿主允许的访问范围。
3. **在什么条件下有效**：长期偏好、过去情况、项目约定或临时场景。
4. **依据是什么**：来源引用、必要证据，以及显式保存或自动形成的依据。

这是概念要求，不是最终字段清单。

Session 是来源位置，不是跨会话记忆天然的唯一所有者。相同用户和角色换一个会话，应仍能找到允许范围内的有效记忆。

角色名可以修改，角色身份保持稳定。复制一个角色定义，不应因为名字或人设相同而自动继承另一角色的记忆。

## 5. 第一版的范围规则

| 使用范围 | 示例 | 规则 |
| --- | --- | --- |
| 当前用户与角色 | “以后你叫我小林” | 可跨这段用户与角色交互中的会话生效；不自动传播给其他角色 |
| 用户共享 | “所有角色都不要给我剧透” | 用户明确允许共享后，其他获得授权的角色可以读取 |
| 项目内 | “这个项目使用英文代码注释” | 只在相应项目范围内生效，不自动流入无关项目或闲聊 |

自动形成的个人记忆默认保留在当前用户与角色的范围内。提升为共享记忆需要用户明确意愿；项目内容也不会因为被总结过就成为全局用户画像。

这些范围可以组合。例如一条项目内的私人交流仍可带有角色限制。共享范围不会覆盖更严格的来源约束，派生结果不能比其依据拥有更广的可见性。

用户要求、角色设定和会话背景可能改变内容的适用条件，但不会自行扩大访问权限。

**访问范围与角色知识边界是两个维度。** “谁获准读取数据”由宿主授权；“某个剧情进度或世界线中的角色应该知道什么”属于角色设定与内容适用性。未来的作品、剧情进度和知识截止点不能替代现有访问范围，也不能扩大权限。本版保留原作资料、虚构事件和真实交互的来源区别；完整的剧情视角策略后续设计，不能声称只过滤记忆就能消除模型先验中的剧透。

## 6. 来源与事实的区别

用户陈述、助手台词、外部资料和 Host 执行回执不是同一种证据。

- 用户说过某件事，应保留这一陈述的来源；未知事实不因被记录就成为已验证事实。
- 助手说“我们去年一起去过海边”，只能证明它说过这句话，不能据此制造真实共同经历。
- 助手承诺执行任务，与宿主确认任务已经执行，是不同事件。
- 原作设定和知识资料可以作为参考，但不是角色与用户的亲历。
- 虚构身份、假设和角色扮演中的事件应保留原有语境，不转写为真实用户画像。
- 同一来源的多次摘要和引用不是多份独立证据。

模型可以解释语义、抽取内容并提出整理结果。来源身份、允许范围、生命周期和执行事实仍由拥有这些信息的组件决定。

事件时间有依据时才记录；缺少逐条时间的旧数据要标明未知，不能用会话文件修改时间冒充事件发生时间。

### 来源契约是接入前置条件

宿主应在权威写入边界提供稳定的来源身份、可辨认的内容版本，以及由 Host 时钟给出的记录时间。消息记录时间与内容描述的事件发生时间分别表达；事件时间可以未知，解释“昨天”等表达时应使用来源当时的时间与时区语境。

接入 Amadeus 时，先统一现有 Session 写入路径的保证：已有路径支持 `turn_id` 与可选 `message_id`，但尚未在所有路径统一逐条身份与时间。复用有效标识，补齐缺口；一个 turn 可以有多条消息，不能直接把 turn 当作唯一来源。历史迁移不能凭空补造发生时间。

来源不限定为聊天消息。未来 Schedule 的运行结果仍由宿主提供稳定引用和真实执行状态。

### 记忆也是行为先例

召回内容会影响模型之后的表达和判断。正确记录了一段台词，不代表它适合反复出现在角色的上下文中。记忆质量必须同时评价事实召回与行为影响。

- 原始对话继续由宿主管理，供追溯、纠正和按需引用；不能用有损摘要替代唯一原始依据。
- 默认向主模型提供事件、陈述、必要依据和适用条件，避免把成段历史角色回复当成风格样本反复注入。
- 角色承诺和判断应保留“说过／答应过”的证据性质，不转写为已经完成的行动或已核实事实。
- 用户要求原话，或任务需要核对具体措辞时，可以按范围取回必要原文。
- 从台词形成事件概述如需模型抽取，应计入形成成本；不假设改写免费，也不假设换成第三人称就能消除先例效应。

启用自动形成前，必须测量错误先例、口头禅和附和行为是否被跨会话记忆强化。

## 7. 用户自定义内容放在哪里

| 用户输入 | 所属位置 |
| --- | --- |
| “这个角色性格沉稳，表达带一点讽刺感” | 现有人格配置 |
| “记住，我练日语时希望你指出错误” | 保留适用条件的长期记忆 |
| “这次先别纠错” | 当前回合或会话要求，不自动覆盖长期偏好 |
| “这个会话不要形成长期记忆” | 宿主和 Eidema 的采集设置，直接约束处理流程 |

临时要求和持久变更应根据用户意图区分。不会把每次临时例外都当成长期偏好，也不会把用户明确的永久纠正当作普通闲聊丢弃。

用户明确固定的要求不能仅因很久没有提及就被自动淘汰。偏好记忆影响回答方式，但不授予宿主工具权限，也不覆盖真实执行结果。

## 8. 前台读取与后台处理

### 前台

- 在宿主提供的身份、范围和当前问题下召回。
- 返回有预算的内容、来源和必要的有效性信息，避免重复注入近期上下文里已有的内容。
- 将记忆作为参考上下文，与稳定角色设定和 Host 规则分开。
- 用户明确记住、纠正和遗忘应立即持久化并影响后续读取，不等待后台周期。
- 未命中或检索失败时，普通对话可以继续；明确回忆问题缺少证据时应如实说明。
- 不以每轮新增生成式模型调用作为常规检索的前置条件。

跨会话可见性不能完全依赖后台摘要完成。对于允许范围内、已提交但尚未整理的近期内容，方案必须明确如何提供有界召回，同时避免与当前上下文重复。

### 后台

- 只消费宿主确认的来源增量；不把已取消的中间输出冒充实际发生的交互。
- 同一来源重送应可识别，不产生重复记忆。
- 在批量、空闲和预算条件满足时形成或整理记忆。
- 对未变化的输入跳过模型调用，避免反复全量总结。
- 按允许范围分别处理，不把不同角色或项目的内容混合整理后再依赖提示词隔离。
- 可以提取、去重、更新和概述事实；本版不生成关系或人格成长状态。
- 后台处理不占有长期数据库写锁，不应争用主对话和语音所需资源。

语义筛选尽量在同一次批处理里完成，不先添加独立的“是否值得记住”模型调用。

## 9. 纠正、遗忘与并发

### 纠正

明确纠正应立即改变当前有效结果。旧记录在有需要时可以作为过去情况保留，但不能继续冒充当前状态。

用户只是提出临时例外时，不应自动废弃长期偏好。没有足够证据的冲突可以保留并明确表达不确定，不由整理器猜出一个“确定事实”。

### 遗忘

遗忘必须作用于相关记忆、派生摘要、检索索引、缓存和在途结果。重新启动、索引重建或再次处理同一被排除来源，都不能将它恢复。

“忘记记忆”与“删除宿主原始 Session/Work 记录”是不同操作，应向用户说明效果。用户以后主动重新要求记住，可以作为新的明确操作处理。

需要保留足以防止重新生成的排除依据，但具体粒度、标识和物理清理方式留待数据设计。不能把简单删除向量行视为完整遗忘。

数据设计应包含不保留被遗忘原值的排除记录（墓碑），关联稳定来源及作用范围。具体应排除一条来源、其中一个片段还是某个派生事实，需与纠正和重放语义一起确定；不能为忘掉一句话而默认排除同条消息中全部无关事实。

遗忘保证覆盖 Eidema 管理的内容与派生状态。宿主原始档案、备份和外部 Work provider 的独立存储需分别说明。外部 agent 是否在委派会话中另行形成记忆，应通过集成验证确认；未经确认不能承诺跨系统删除，也不能默默修改 provider 的全局记忆设置。

### 并发

后台任务和读取结果必须与有效版本一致。用户纠正、遗忘、撤回来源或切换归属之后，过时结果不能重新写回或进入新的回合。

这要求版本和失效机制，而不要求额外的模型审查链。最终的事务、版本字段和任务恢复方式属于下一阶段设计。

一次生成应使用一致的已提交记忆视图，后续回合可以看到新的有效版本。不能把整个 Session 冻结为唯一刷新单位：持久 agent 的会话可能很长，后台工作也会产生新事实。快照的一致性不能代替后台提交时的有效性判定；在途结果仍受纠正、遗忘与来源撤销约束。

## 10. 运行成本与可观察性

预算至少区分：

- 前台新增检索时间。
- 注入主模型的额外上下文。
- 后台抽取、去重、更新、合并等实际模型调用与 token。
- 常驻内存、CPU、显存、磁盘和索引增长。
- 内容提交到可召回的延迟与后台积压。

异步只改变阻塞位置，不会消除计算费用。预算耗尽或处理失败时，要保留可恢复的待处理状态和可诊断原因，避免无界重试或静默丢弃。

具体模型、默认启用策略、批次大小、并发数、token/费用限额和截止时间尚未定案，应通过相同输入和场景比较后确定。

常驻偏好与按需召回应分开预算，记录实际 token 数、缓存命中及上下文中的位置。字符占比只能提示风险，不能直接证明人格影响强弱；不预设 1–2k tokens 是合适的默认记忆量。后台调用、失败重试、embedding 和重建成本均计入实际消耗。

## 11. 给后续人格能力保留的位置

本版以四项实际能力支持未来扩展：

1. 稳定的用户、角色和项目身份。
2. 清楚的来源、访问范围、适用条件和有效状态。
3. 可追溯、可撤销的派生结果。
4. 返回记忆内容与来源的读取边界，供不同人格和主模型使用。

后续人格模块可以据此推导关系和互动状态。本版不加入没有使用方的关系分数、情绪字段、人格状态机或专用成长模型。

初版仍需评价开启记忆前后的人格保真与长期漂移。简短人格重锚定可以作为实验变量，有证据再决定是否启用。自然语言关系笔记与结构化慢状态的比较属于后续人格研究，不成为 v1 的实现前置条件。

## 12. 最小验收旅程

| 情景 | 预期结果 |
| --- | --- |
| 明确记住后开启新会话 | 在同一允许范围内找到内容与来源 |
| 后台尚未整理就切换会话 | 已提交的近期内容不会因处理滞后表现为完全丢失 |
| 切换角色或项目 | 不召回未授权范围的内容 |
| 用户允许共享某项偏好 | 授权角色可使用；不连带共享其他记忆 |
| 用户纠正长期偏好 | 新值立即有效；过去值不冒充当前值 |
| 用户提出临时例外 | 当前交互遵从例外，长期记忆保持原适用条件 |
| 用户要求遗忘时后台仍运行 | 后台、缓存、在途读取不能恢复旧内容 |
| 重启、重建索引、同一来源再次导入 | 范围和遗忘效果保持，重复输入不生成重复记忆 |
| 人设修改或角色改名 | 稳定身份对应的记忆仍可读取，核心人设不被后台改写 |
| 复制角色定义 | 新身份不自动继承旧身份记忆 |
| 助手虚构、角色扮演或原作资料 | 不被写成真实用户经历 |
| 中文提问，证据在日文或英文回复中 | 测量跨语言命中与回答依据，不能用单语言结果替代 |
| 历史包含一次口头禅、错误回答或附和 | 比较有无记忆时是否反复复制并跨会话强化 |
| 记忆引用中含“忽略规则”等指令 | 不扩大权限、不改写人格配置、不成为新的执行授权 |
| 开启记忆后进行长对话 | 测量人格漂移与偏好遵循；召回正确率不能替代行为评价 |
| 检索或后台模型不可用 | 普通对话继续，缺失与待处理状态可解释 |
| 后台与主对话、ASR/TTS 同时运行 | 能测量并限制额外延迟、调用量和设备资源 |

## 13. 接下来的设计问题

以下问题尚未定案：

- 来源、记忆、证据关联和排除记录的最小数据结构。
- 记忆更新与历史版本的表示；遗忘的最小粒度。
- SQLite 存储布局、派生索引的选择、迁移、导出及备份行为。
- 中文、日文与英文的词法检索，以及是否启用语义检索。
- 对近期未整理内容的召回方式。
- 自动形成的默认开关、批次与空闲触发条件。
- 后台 token、调用次数、费用和设备资源预算。
- 实际使用方需要的最小接口。

这些选择应服务于本文的行为约束，并通过合成场景验证，不提前搭建通用框架或实现尚无使用方的功能。

## 14. 基线、对照与设计顺序

先定义来源契约和记忆生命周期，再设计逻辑数据模型、存储、检索与后台预算。初版的讨论起点见[数据与 runtime 设计讨论稿](v1-data-runtime-proposal.md)。

“可访问的原始来源 + 检索 + 显式记忆”是主对照。抽取和后台整理必须证明对质量、时序正确性或成本有明确增益，不能以项目宣传分数决定采用顺序。保存原文不等于每轮注入原文，原文与事件表示的对照应与后端选择分别测量。

对照前写清相同的数据、范围、预算、留出场景和采纳条件；分别报告检索命中、回答正确性、行为影响、遗忘可靠性与开销。外部项目和论文的成绩不是 Eidema 的复现结果。
