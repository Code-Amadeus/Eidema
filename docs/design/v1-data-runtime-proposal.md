## 1. 先设计语义与生命周期，再决定表和语言

初版最重要的是让数据模型准确表达：这是谁的内容、依据是什么、何时成立、更正改变什么、遗忘排除什么。字段与索引由这些语义推导。

建议依次回答：

1. **来源契约**：哪些已提交记录可以进入记忆，如何稳定引用，修改与重送如何辨认，如何撤回授权。
2. **生命周期**：显式记住、临时例外、永久纠正、过去情况、遗忘和重新授权分别产生什么效果。
3. **逻辑数据模型**：哪些是权威数据，哪些是可重建的派生结果；分别由谁写入。
4. **工作负载与存储检索**：数据量、语言、写入频率、并发、允许延迟和设备资源。
5. **运行方式与实现语言**：嵌入宿主还是独立进程，后台如何恢复和限额，语言收益是否覆盖集成成本。

不能先建立一个只有 `text + embedding + score` 的通用列表，再把来源、遗忘与权限补成提示词规则。

## 2. 五组逻辑记录

这是设计讨论的分组，不要求恰好五张表。

| 分组 | 需要表达的内容 | 权威归属与待确定问题 |
| --- | --- | --- |
| 来源引用 | 宿主来源身份、内容版本、类型、原文位置、记录时间、允许范围 | Host 拥有原始记录与授权；Eidema 保存引用及必要证据。需确定稳定片段的定位与失效方式。 |
| 记忆条目 | 内容、涉及对象、适用条件、当前有效状态、显式保存或自动形成的性质 | Eidema 管理记忆生命周期；明确用户变更优先于旧派生结果。需区分曾经成立与已经错误。 |
| 依据关联 | 哪些来源的哪个版本支持条目；必要的证据片段与归属 | 多个来源可以支持同一条目，一条来源也可以支持多个事实；重复摘要不增加独立证据数。 |
| 排除记录 | 被排除的来源或片段、作用范围，以及防止重放所需的标识 | 不保留被遗忘原值。需确定部分遗忘的粒度、旧备份恢复与用户重新明确授权的语义。 |
| 维护进度 | 来源游标、正在处理的输入版本、完成或失败状态、索引版本、预算消耗 | 只管理记忆维护。不能演变成第二套通用 Schedule 或 Work Ledger。 |

词法索引、向量索引和缓存是派生物，不能成为唯一保存事实或唯一执行遗忘的地方。用户的核心人格配置仍在宿主，不复制成另一份可自动改写的记忆。

数据模型现将逻辑分组细化为九张核心表：费用尝试独立于任务详情；依据区分组内共同必要与组间可以替代；合并保留旧写入身份。删除聊天保留显式记忆，因此 Host 核准的最小操作凭据由 Eidema 同库保存，不能只引用可删除的聊天消息，也不要求为此新增 Host 凭据库。

### 来源身份与时间

- 通用契约使用 Host 提供的来源引用，不要求所有宿主都有 Amadeus 的 Session 类。Amadeus 适配器可以映射已有 `message_id`、`turn_id` 与 Work 记录。
- 来源身份应稳定；内容发生变化时，需要能辨认引用的是哪个版本。同一 turn 的多条消息不能相互覆盖。
- 消息记录时间、事件发生时间、记忆形成时间不是同一个时间。未知的事件时间保留未知；旧数据导入时间不能冒充原消息时间。
- 相对时间应结合来源当时的 Host 时间与时区解释。现在重新索引，不能把过去的“明天”改成重新索引后的明天。
- “谁能读”与“剧情中的角色应该知道什么”分别建模，不用一个三档可见性枚举承担全部语义。

### 一个需要先说清的例子

用户先说“我平时喝咖啡”，后来说“最近改喝茶”，然后要求“忘掉我喝咖啡这件事”：

- 第二句话可能表示偏好发生变化，不等于第一句话从未成立；当前召回不能混为矛盾的两个现值。
- 第三句话要求移除相关记忆及派生结果，并阻止从旧来源再次形成。
- 同条旧消息中若还有其他事实，不能未经意图判断就全部排除。
- 如果用户只说“今天喝茶”，则不应自动更新长期偏好。

能准确表达这组操作，比现在确定 Rust struct 或 SQL 列名更重要。

## 3. 存储与检索的主对照

当前建议：**SQLite 保存 Eidema 的权威状态，原始 Session／Work 档案仍由 Host 管理；FTS5 和可选向量索引作为派生检索。** Markdown 可用于查看、导出与人工审阅，不同时承担第二套可写真源。

检索基线需要包含：

- 按消息或有明确边界的片段访问获准的原始来源，保留来源引用；
- 显式记忆、适用条件、时间与访问范围；
- 词法检索，以及单独评估的多语言语义检索；
- 有界候选集、去重、有效性判断和上下文预算；
- 对刚提交但尚未整理的来源提供有界召回。

范围限制应进入候选检索过程，不能先全库取很小的 top-k 再删掉无权限项，使合法结果被挤出。返回正文前还要保证结果仍然有效，索引过期不能恢复被遗忘的内容。

**FTS5 是词法工具，不自动解决中日文分词或跨语言语义。** 默认 `unicode61` 按连续字符类别分词；`trigram` 的全文查询对少于三个 Unicode 字符的子串不能命中。分词器、短词检索和中文问题召回日文证据必须实测，多语言 embedding 也不能仅凭模型名被视为已通过。[SQLite FTS5 文档](https://www.sqlite.org/fts5.html#tokenizers)

主对照与挑战者应分开考察两类问题：

1. **检索和形成方式**：原始来源检索与显式记忆，对比 EverOS、Hindsight 及可选 C8 核心思路。相同来源、访问范围、预算和留出场景，先定采纳标准。
2. **送给主模型的表示方式**：原文片段与有依据的事件表示。不能因某方案同时更换后端、改写内容和增加 token，就把结果全部归因于后端。

自动形成与整理需要证明增益。使用外部参考实现作为实验工具，不意味着把该框架变成 Eidema 的核心依赖。

## 4. 长期保存不等于全部常驻内存

持久 agent 可以长时间保存大量数据，也可以在无工作时不做模型推理。runtime 只需要持有本次请求、有限的连接和缓存、有限的后台任务；原始来源与主要索引应按需访问。

容量应按来源条数、平均长度、向量数量与维度、索引开销和保留策略测量，而不是只按“运行了几年”判断。

例如，100 万条 384 维 float32 向量，原始数值约占 1.54 GB（约 1.43 GiB），尚未包含索引、元数据和正文。这只是容量计算，不是本项目的规模目标或常驻内存预测。换成 Rust 不会消除同一向量表示所需的数据量；是否常驻、如何分页与索引，会显著影响实际 RSS。

前台延迟需要拆开测：

> 范围与有效性查询 + 可选的查询 embedding + 索引检索 + 候选读取与组合 + 上下文组装。

这是一份开销分解，具体阶段可能并行。磁盘冷启动、模型冷启动、数据库写锁、候选集大小和额外模型调用都可能成为瓶颈。现阶段尚无基准支持“某一种语言端到端最快”的结论。

## 5. runtime 语言方向

**已选择 Python + SQLite 作为初版方向。** 这是对集成成本与当前任务形态的判断，不是 Python 性能必定足够的保证。Rust 保留为之后有实际瓶颈或部署需求时再评估的选项。

| 选择 | 当前收益 | 需要承担的成本 |
| --- | --- | --- |
| Python 库，嵌入现有宿主 | 复用现有模型接入与部署环境，便于迭代数据语义和评测；无需新增跨进程协议 | 需显式限制对象、缓存和队列规模；CPU 密集逻辑及阻塞 I/O 不能占用主事件循环 |
| Rust 核心，通过绑定接入 Python | 可控制原生数据布局；在大量 CPU 逻辑与对象管理场景中值得测量；适合明确的系统组件边界 | 增加绑定、打包、平台构建、取消和错误传递的维护；无法自动修复错误索引或减少模型计算 |
| Rust 独立本地服务 | 不同语言可通过协议接入，具备进程隔离 | 增加进程生命周期、IPC、版本匹配与部署工作；本版尚没有多语言并行消费者要求 |

Python 的 `sqlite3` 调用的是 SQLite C 库，核心 SQL／FTS 查询并不是由 Python 逐行解释执行。Rust 的所有权机制可在不依赖垃圾回收器的情况下提供内存安全保证，但这不等于自动获得有界缓存、无泄漏或端到端最高吞吐。[Python sqlite3 文档](https://docs.python.org/3.12/library/sqlite3.html)、[Rust 所有权说明](https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html)

Eidema 的核心包应独立于 Amadeus 的全局状态和业务类；由 Amadeus 适配器提供来源、身份、授权和必要的模型能力。独立复用不要求初版就同时交付多语言 SDK、daemon 和网络服务。

考虑引入 Rust 的证据应是：

- 在代表性输入下，已定位 Python 自身的 CPU 热点或对象内存开销，且合理的批处理与有界缓存仍不能满足目标；
- 确认该部分是足够稳定、可隔离的核心，并计入跨边界调用与数据复制成本；
- 或部署目标明确改变为独立原生组件，团队愿意承担相应发布和维护工作。

如果瓶颈在 SQL／索引，就先优化查询与索引；在 embedding 或主模型，就先优化模型路径；在后台并发，就先控制资源。无需为了保留未来选择而现在实现多套 runtime。

## 6. 后台整理与长期运行

建议初版从一个有界的维护执行单元开始，确切线程或进程方式由阻塞特性和测试决定：

1. 来源先有稳定提交记录，再推进持久化处理游标；重启后可以继续，重送不会生成重复事实。
2. 无来源变化时不调用形成模型；普通检索不强制经过生成式模型。
3. 模型调用和大批扫描不占有数据库写事务；短事务提交时验证输入及排除状态仍有效。
4. 不把阻塞数据库调用直接放进聊天、语音使用的事件循环；连接归属和并发方式必须明确。
5. 预算分别限制批次输入、输出、实际调用量、embedding、失败重试、设备资源与积压；额度耗尽应留下可恢复进度。
6. 缓存、候选数量与任务队列有界；重建索引要限速，前台工作优先获得必要资源。
7. 一次生成读取一致视图，下一回合可使用新提交版本；不依赖“Session 结束”才刷新。
8. 每次外部调用前原子预留预算，已知实际用量后替换预留，未知结果保守占用。任务清理不能丢掉费用；迟到且未采用的结果同样计费。

SQLite 每个数据库文件同一时刻只有一个写入者，增加工作线程不能改变这个约束。WAL 可以改善读写并行，但需要控制事务持续时间和 checkpoint；长读事务可能阻碍 checkpoint。最终选用的 SQLite 版本与配置应验证实际使用的 FTS、WAL 和恢复行为。[SQLite 适用场景](https://www.sqlite.org/whentouse.html)、[WAL 文档](https://www.sqlite.org/wal.html)

后台维护处理记忆；宿主 Schedule 决定何时执行已授权的其他工作。即使将来由同一宿主协调预算，也不混用任务状态。

## 7. 先约定测量，再冻结选型

下一份具体设计应明确目标机器、预计来源增长、活跃角色与并发量，然后给出可执行的验收阈值。可以用逐级增长的合成数据测容量曲线，但不能把某个条目数当作跨设备通用的性能保证。

| 维度 | 需要记录 |
| --- | --- |
| 正确性 | 当前与历史事实区分、跨语言召回、依据可追溯、范围隔离、纠正与遗忘后的结果 |
| 行为影响 | 口头禅与错误先例传播、有无记忆的人格保真与附和程度、长对话中的偏好遵循 |
| 前台开销 | 冷／热检索的 p50、p95，查询 embedding，注入 token 与缓存情况，对主对话／语音延迟的影响 |
| 常驻资源 | 空闲和工作时的 RSS、CPU、磁盘与索引增长，持续运行后的资源趋势 |
| 后台成本 | 每批及累计模型开销、重复处理量、失败重试、积压、提交到可召回的延迟 |
| 恢复与失效 | 进程退出后重启、后台与遗忘同时发生、同一来源重放、索引重建与来源撤回 |

固定数据与模型配置、保留未见场景、记录失败和实际用量。服务端模型即使提供 seed 也不应被假定完全可复现。项目作者报告的性能只用于提出假设，不能代替 Amadeus 场景中的测量。

具体可参考的外部任务、指标和覆盖差距见 [Benchmark 参考](benchmark-references.md)。当前只记录参考，不运行评测，也不设计自有 benchmark。

第 2 节已在[初版数据模型](v1-data-model.md)中细化为字段与操作流程；[检索与上下文方案](v1-retrieval-context.md)给出候选流程及实验预算。接下来确认语义并验证方案，再冻结 schema 和查询。当前不开始 runtime 实现。

## 8. Amadeus 接入复核与待收敛契约

下面只记录已经核查的接入事实和设计约束，不把评审建议直接升级成已冻结的 M0／M1 计划。用户提出的候选审查、热温冷关系仍待继续思考；本轮不新增设计文件、测试实现或评测工程。

| 核查事实 | 对接入的要求 |
| --- | --- |
| 主对话把最多 60 条 history 放入 frame；当前决策日志以 INFO 写 frame 与模型原始输出 | 遗忘需覆盖之后的模型可见投影；默认日志只保留必要元数据，不能留下正文副本。[prompt 与日志](https://github.com/Code-Amadeus/Amadeus/blob/9547f39ad518134ce4594f5a52a92c8a61629f45/server/cooperative_provider_loop.py#L1126)、[日志隐私工具](https://github.com/Code-Amadeus/Amadeus/blob/9547f39ad518134ce4594f5a52a92c8a61629f45/config/log_privacy.py#L12) |
| role_reference 在 acceptance_check 之前执行，且异常与主决策共用失败处理 | 可以在投机阶段只读召回；Host 在调用边界隔离记忆超时／错误，保留正常取消语义，不能把可选召回失败升级成整轮失败。[调用顺序](https://github.com/Code-Amadeus/Amadeus/blob/9547f39ad518134ce4594f5a52a92c8a61629f45/server/cooperative_provider_loop.py#L1657) |

| 已有角色人设配置，但未找到通用的对话写入常驻用户要求层 | 回复规则由 Eidema 保存与审查，不把缺失的 Host 设置层当成前提；人设和执行配置继续归 Host。[角色配置](https://github.com/Code-Amadeus/Amadeus/blob/9547f39ad518134ce4594f5a52a92c8a61629f45/core/character_profiles.py#L116) |
| 主回复语言权威目前是日语／英语；字幕翻译不等于改变回复与 TTS 的语言 | “以后用中文回答”需经过实际设置能力处理，不能保存一条记忆就宣称执行成功。称呼文字与 TTS 读音同样分别处理。[语言权威](https://github.com/Code-Amadeus/Amadeus/blob/9547f39ad518134ce4594f5a52a92c8a61629f45/server/assistant_language.py#L1) |
| T1 core／T2 voice 不默认包含本地 e5 所需的完整依赖；角色 RAG 在首次引用时才加载 | 先报告真实的 FTS-only 能力；向量作为可选能力，不阻塞第一轮加载或下载。OpenCC、ONNX 也不能因为出现在 local-models extra 中就视为基础安装已有。[安装层级](https://github.com/Code-Amadeus/Amadeus/blob/9547f39ad518134ce4594f5a52a92c8a61629f45/pyproject.toml#L9)、[惰性加载](https://github.com/Code-Amadeus/Amadeus/blob/9547f39ad518134ce4594f5a52a92c8a61629f45/core/character_rag.py#L171) |

会话入口应沿用“角色提议、Host 接受操作”的分工。角色在提交前不能宣告已经保存；界面回执只在持久提交后出现，失败则明确反馈。仅把界面称为权威、却允许语音先说“已保存”，仍会给用户错误确认。若要语音确认，可由 Host 在提交后使用已有表达路径，不必增加一次解释模型调用。

更正和遗忘可以使用本轮已展示的标识，也可以先通过只读解析取得合法目标；Host 校验身份、版本、范围和用户意图。没有展示过的目标不等于必须转去界面，未关联提及也不一律追加确认；有歧义才澄清。检索状态应区分未启用、无命中、部分覆盖和失败，不能让主模型猜测完整性。task_lookup 的失败记录提示了这一风险，但不是记忆场景的实测结果。

### 最小调用关系，尚未冻结为 API

| 交互 | 必须保持的契约 |
| --- | --- |
| 接收来源 | 稳定 namespace／record_key／revision；已提交的规范文本与当时语境 |
| 保存／更正 | 已获准的操作与稳定项键；目标预期版本；保存凭据、内容及依据同事务 |
| 撤回来源 | 明确目标、原因和本次操作身份；删除聊天不连带删除独立保存凭据，不能只以来源版本三元组代表所有撤回操作 |
| 解析／提交遗忘 | 解析只读；提交固定目标集并使用稳定 forget_id；下一次 Host 投影同步排除 |
| 召回／读取已采用规则 | 当前身份、语境、预算、截止时间及实际已展示片段；返回版本、覆盖状态与未提供原因 |
| 查看／状态 | 可解释当前记忆、采用情况、容量、清理进度及实际 SQLite／索引能力 |

standing(scope) 可以是只读采用视图的接口候选，但不能现在就硬编码为一组字段筛选；适用条件、冷路径审查状态和容量语义尚未收敛。未审查的候选不能自动冒充已生效要求。

上述回复规则归属针对 Amadeus 集成。其他宿主若已有自己的原生用户指令功能，可以保留该权威入口而不用 Eidema 的采用视图；集成时明确唯一写入归属，不能维护两份互相覆盖的要求。

保存凭据同库提交后，仍需验证合并后的键与引用契约，暂不删除 merged。若最早版本承诺跨重启完成遗忘清理，就必须有持久的清理进度；不能只因自动形成后置，就把所有维护状态一并推迟。先界面还是先会话入口、最终表集合及测试合并方式保持待定，不在本轮开始实施。

当前可以独立启动的下一步是 Amadeus 来源基础：消息 id、逐条时间、修订、规范投影、日志隐私和可选召回失败隔离。它们不依赖温路径或冷路径审查的定稿。随后再实现显式记忆的保存／更正／遗忘闭环；本轮只记录顺序，不编写实现。现有 Session 的 timestamp 是保存时间，用户消息尚缺逐条 id 与时间，助手仍存在正文哈希回退，不能把这些基础标为已完成。[当前消息写入](https://github.com/Code-Amadeus/Amadeus/blob/9547f39ad518134ce4594f5a52a92c8a61629f45/core/session_manager.py#L496)

### 环境与发布边界

Python 3.12 的 python.org 常规二进制发布停在 3.12.10，之后进入源码安全更新阶段；这说明应核查实际 SQLite 构建，不说明任何 Python 3.12 环境都无法获得修复版。uv 管理的其他 Python 小版本也不能代替对目标 3.12 构建的检查。[PEP 693](https://peps.python.org/pep-0693/)

单一写入及 checkpoint 所有者、真正只读的检索连接与受维护 SQLite 版本共同构成部署方案。query_only 并不禁止 checkpoint，兼容旧版的条件不能省略；具体见[数据模型 §10](v1-data-model.md#10-sqlite-约束与提交边界)。本轮未运行并发、落盘或断电测试。

Eidema 的许可选择仍需仓库所有者确定，复用目标不等于已授予开源许可；不能从“没有许可证”进一步推导 GitHub 上连查看或 fork 都不允许。[GitHub 许可说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository) 本轮不选择许可证，也不对外回复社区提案。
